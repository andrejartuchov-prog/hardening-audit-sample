Hardening audit · a sample run

A working sample of the audit — run end to end on a public codebase

Before you hand anyone your platform, you should be able to see how they work. So instead of describing my method, I ran it.

The subject is an open-source FastAPI payments and subscriptions platform of the same class as yours — Python, PostgreSQL, multi-tenant, real money paths, a large test suite. It is public, so I can show the work in full; it is not your system, and I say that plainly.

To be exact about what this is and is not: this is that platform's code, not yours. I have not seen your platform. Nothing on this page is a claim about it, and nothing here predicts what I would find in it. What this page shows is depth and method — how I look, what I look for, and what a finding looks like by the time it reaches you.

One thing worth saying up front: this is a mature, security-minded codebase — not a soft target. Tenant isolation is genuinely strong, capability tokens are hashed at rest, and the obvious classes of defect simply are not there. The findings below are the ones that survived that scrutiny — and that is the point. On a system that is well built and well tested, the failures that remain are not sloppy ones. They are structural, and they are invisible to tests that pass.

The subject is a real open-source payments platform; I do not name it, and I have anonymized file and symbol names — I don't publish identifiable unpatched findings about third parties. This is anonymization, not staging: the run, the mutations and the test output are real.

Three findings, in the shape you would receive them

Each one below is delivered the way every finding in your report would be: priority, what is broken, how to reproduce it, how to fix it. Three are shown here out of thirteen — picked to span the method rather than to stack up severity.

P0Security Rate limiting can be switched off by the caller

What's broken

The rate limiter counts requests per caller. It works out who the caller is from the token or session cookie attached to the request — before checking whether that credential is real. Every distinct value counts as a distinct caller, so an attacker who sends a fresh piece of junk on each request lands in a fresh counter every time and the limit never accumulates.

The junk request is not rejected either. An unrecognized session cookie is treated as anonymous rather than refused, so the request carries on to the endpoint — and anonymous is all these endpoints need.

This is the platform's only anti-brute-force control, and it sits in front of login, one-time email codes, TOTP, backup codes, customer-portal sessions, checkout confirmation and license-key validation.

How to reproduce
Take one rate-limited public endpoint and call it a hundred times as an ordinary client: the limiter engages after six requests and blocks for fifteen minutes. Repeat the same hundred calls, changing the session cookie to a new random value each time. Zero blocks. Every request is served.
How to fix
Identify unauthenticated callers by their network peer, not by a value they choose. Any credential that does not resolve to a real subject should collapse into one shared bucket per IP, so rotating junk cannot mint new counters. Use a token as identity only after it has been validated.

P0Money correctness The same payment event can be processed twice

What's broken

Every incoming payment event passes one guard: it asks whether the event has been handled, runs the handler, and marks the event handled only afterwards. Between the question and the mark there is no lock and no atomic claim. The worker commits once, at the very end — so a second attempt that begins in the meantime cannot see the first one's mark, passes the same check, and repeats the same side effects. This single guard stands in front of roughly twenty handlers, successful payments, charges, refunds and disputes among them.

Two entirely ordinary things trigger it. The queue delivers at least once by design and re-sends a message whose visibility window expires while the first attempt is still running. And a support action in the back office can re-queue an event that is already being processed.

The project itself carries an admission of this race in its own code: a comment in the payment path says, in as many words, that another worker may have created the transaction after the check was made. This is not an auditor's hypothesis — it is an acknowledged property of the system that was never closed at the webhook gate.

How to reproduce
Take a stored payment event that has not been marked handled, and run its handler twice concurrently from two separate database sessions. Both pass the check, both perform the side effects, both mark it done. Without touching the code at all: hold the handler longer than the queue's visibility window, and the queue re-sends the message on its own.
How to fix
Claim the event atomically instead of checking a flag: one conditional update that marks it handled only if it was not already, and stop if the claim returns nothing. The project already uses row-level locking in eight other places, so this is its own established pattern — it was simply never carried through to the webhook gate.

P1Data & compliance Tax can silently come out as zero

What's broken
The tax calculation has two modes: raise an error, or quietly return zero. Quiet is the default. The module's own comment explains why that is dangerous — draft orders created off-session save the result and never recalculate it, so a silent zero becomes a completed sale with no tax on it, and the caller is expected to surface the error instead. Strict mode is passed explicitly in exactly one place, while the shared path that computes order amounts calls the function without the flag — which means quietly.

This is a class of defect worth naming on its own: a default is making a decision that nobody chose.

How to reproduce
Make the tax provider fail on a subscription order — an incomplete address is enough. The order saves with tax at zero, a warning goes to the log, and nothing surfaces to the caller or to the customer.
How to fix
Remove the default and make the flag required, so every call site has to state out loud whether a silent zero is acceptable there. At the moment that decision is being made by omission.

A green test with the right name guarantees nothing

The right question about any green suite is whether it is actually checking the code. It has a concrete answer: break the logic on purpose, and see whether the suite notices.

I did that twice on that same codebase. Both times I measured against a baseline first — without one, "green after the change" proves nothing, because the suite could have been red before it.

Money — the rule that stops a customer spending more credit than they have A single clamp in a single function. I did not delete it — I added an early return in front of it, for exactly the case where the balance is smaller than the order, so the clamp below is never reached.
Broken on purpose — product code
--- billing/amounts.py (upstream)
+++ billing/amounts.py (MUTATED)
 def apply_credit_balance(total_amount, customer_balance):
     if total_amount >= 0:
+        if 0 < customer_balance < total_amount:
+            return -total_amount
         return -min(total_amount, customer_balance)
     if customer_balance < 0:
         return min(-total_amount, -customer_balance)
     return 0

In production this means a customer holding $10 of credit settles a $50 order entirely with credit — the order is paid, and nothing remains to charge.

Why the suite stayed quiet: that function has four dedicated tests. They pin the matrix of signs — order positive or negative, balance positive or negative. Not one of them sets an amount where the clamp matters; in every fixture the balance already exceeds the order. The tests check that the sign is right. They never check that the limit exists.

In production that is a cross-tenant leak — one seller's ordinary API token reading every other seller's orders, amounts and customers.

Why the suite stayed quiet: there are four tests named test_cross_tenant_order_access_denied, so isolation looks covered. All four run as a user. The code branches on four kinds of caller, and the tenant branch is covered only by a test that its own data is visible — never that someone else's is not. The test is named after the subject and exercises one path out of four.

What both have in common, in one line: a test only checks what is observable in its own data. If no fixture contains the case where a protection fires, that protection can be deleted and nothing turns red.

That is the check I run against a large green suite — not whether the tests pass, but which of them would fail if the logic underneath them were wrong.

How the audit is organized

Four axes.

1 · Security
Authentication and sessions, multi-tenant isolation in the application and in the database, payment and webhook paths, secrets, injection and XSS, rate limiting.
2 · Data & compliance
How PII is handled, data privacy in GDPR-class terms, cross-border transfer, retention.
3 · Correctness
Settlement and refund money logic — the highest-stakes path in a system like this — and whether the green tests are meaningfully green.
4 · Reliability & code quality
Error handling, N+1 queries, oversized functions, resilience.

Every finding arrives in the shape you saw above: priority, what is broken, how to reproduce it, how to fix it — with reproductions that run rather than reproductions that are described. Where an axis comes back clean, that is a result too, and it ships with the evidence that the check actually ran. A finished audit is coverage of the agreed checks, not a tally of holes.

The work runs on a scoped read-only copy, without production access and without production secrets.

Subject of this run: an open-source payments platform of the same class as the systems I audit. No client code, systems or data were involved at any point.
